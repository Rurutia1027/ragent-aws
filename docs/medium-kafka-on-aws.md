# 把 Broker 留在集群外面

## 一套 Agentic RAG 上 AWS 时，为什么放弃 SQS，并把 Kafka 交给 MSK

Ragent 今天能在一台机器上跑完。问答进程无状态，登录和排队在 Redis，文档放在对象存储，向量放在 PostgreSQL。真正会在后台跑很久的只有三件事：把一份文档切块并写入向量，删掉一个知识库之后回收底层数据，以及把用户的点赞点踩落库。这三件事走消息队列，现在的实现是 RocketMQ。

下一步是把同一套系统放到 EKS 上。副本数、Ingress、健康检查都还在后面。先要定的是这三条消息的去处。AWS 上最省事的答案是 SQS。我们没有选它。计算放在 EKS，消息日志放在 Amazon MSK，由 MSK 维护 Broker。这篇把这个决定写下来，后面改代码时不再重新争论一遍。

## 单机上，这套消息已经有一个明确的承诺

文档分块和知识库清理用的是事务消息，不是发完即忘。

分块的本地事务做一件事：把文档状态改成「执行中」。知识库清理的本地事务做另一件事：把知识库软删。RocketMQ 的做法是先放一条别人看不见的半消息，本地事务成功才让它可见。进程如果死在中间，Broker 会回来问一次。分块的回查看文档是不是已经处于执行中；清理的回查看这条知识库是不是已经查不到。查得到承诺，消息就放行。查不到，消息就丢掉。

反馈不走这条路。点赞是一次普通发送，丢了用户可以再点。

这个承诺在单机上成立，是因为 Broker、数据库和唯一一个应用进程住在一起。人可以登录那台机器看日志。队列积压了，看一眼控制台就知道。

## 拷到多台机器上，承诺还在，事实来源没有跟着走

原项目把公平排队、登录态、定时任务锁放进了 Redis，所以 API 副本本身可以水平扩展。消息这一层没有做同样的事。

消费组名字带了一个可选的 `unique-name`。本地开两个进程时，用它把队列隔开，这个设计是对的。到了集群里，如果每个 Pod 拿到的名字不一样，同一条分块消息会被每个副本各处理一遍。生产配置必须让所有副本共用一个组。这是部署约束，代码不会帮你拦住。

模型熔断记在进程内存里。一个副本认为供应商不可用，另一个副本仍会继续打。健康检查也还没有：进程起来了，不代表数据库和队列已经连上。队列有没有积压、一条分块卡在「执行中」多久，没有一个可以告警的数字。

这些不是功能清单上的遗漏。它们是同一件事：失败发生在另一台机器上时，系统缺少一个共享的事实来源。一致性、投递是否可靠、值班的人能不能看见，在单机里靠「就这一个进程」凑合过去了。EKS 上这个前提没有了。AWS 这一版要补的就是这一层，而不是再加一个检索通道。

## SQS 省掉的是 Broker，省不掉那个承诺

SQS 我们认真对过。它在 AWS 上是默认选项，运维面积最小，也没有 Broker 磁盘这种故障。放弃它，是因为这三条消息里有两条的价值就在那个承诺上：数据库提交了，消息才允许被消费。

SQS 没有半消息，也没有回查。换成它之后，分块和清理的一致性还在，只是从 Broker 协议变成我们自己要写的发件箱。该写的代码一点不少。SQS 真正省掉的是进程和磁盘。

它同时省掉了日志。消息处理完就删除，不能按原样重放。分块因为模型超时失败时，我们希望拿着原来那条消息再跑一次，而不是只靠数据库里一个「执行中」去猜当时的意图。以后要给监控接上同一条事件，标准队列也只有一组竞争消费者。要再加一个旁路，就得在前面放 SNS，变成「一个主题、多条队列」。那时候复杂度回到了 Kafka 已经有的模型：一个 topic，多个消费组。只是组件换了名字。

反馈事件其实适合 SQS。处理完可以丢，只有一个消费者。分块和清理不适合。三套语义里两套对不上，就不值得为了那一套把消息层拆开。

## Broker 不进 EKS

Kafka 可以装进集群。业界也有人用 Operator 自己养 Broker。我们不这么做，和数据库、Redis 是同一条理由。

Broker 要磁盘，要控制器之间的仲裁，要跨可用区。这些故障和 Java 进程的滚动发布不是一种故障。API 副本挂了，拉起来继续接流量。Broker 的磁盘满了，分块停，清理停，反馈停。把这种状态放进同一组节点，等于让问答服务的发布窗口去赌消息系统的磁盘。

MSK 负责 Broker 的补丁、故障检测和多可用区。我们选定规格，不登录机器改配置。EKS 只跑无状态的 API、MCP、前端，以及加进消费组的消费者线程。生产者和消费者仍是应用代码。位点、重试、幂等也仍是应用代码。托管的是进程和磁盘，不是「消息一定会和数据库一起成功」。

这就是混布。每种状态放在已经会运维它的服务上。

| 状态 | 放在哪 |
|:---|:---|
| 问答、工具服务、页面 | EKS Deployment |
| 业务表和向量 | RDS PostgreSQL |
| 登录、排队、锁 | ElastiCache Redis |
| 文档和图片 | S3 |
| 分块、清理、反馈的日志 | MSK |

集群里看不到 Kafka 进程。应用只拿一组 bootstrap 地址。

## 混布具体怎么接

MSK 和 EKS 放在同一个 VPC 的私有子网里。三个可用区，三个 Broker，副本因子 3，最小同步副本 2。认证用 IAM，端口 9098，Pod 通过自己的角色发消息和拉消息，不把长期密钥写进环境变量。安全组只允许节点访问这一个端口。

topic 事先建好，各三个分区，名字沿用现在的三条链路：文档分块、知识库清理、消息反馈。分区键分别用文档 id、知识库 id、`用户:消息`。同一份文档的分块命令落在同一个分区里，顺序就还在。

生产者 `acks=all`，并打开幂等生产者。消费者关闭自动提交，处理成功才提交位点。处理失败不提交，让这条消息再投递。清理任务保持现在的行为：向量、对象存储、索引、图谱哪一项失败，就让整条消息重试；每一项自己可以重复执行。

消费组每条链路一个，所有副本共用。不要给每个 Pod 一个 group id。那是把 `unique-name` 的坑换个名字再踩一次。

## 一致性要写成两段，不能指望 Kafka 事务

Kafka 事务保证的是多条消息一起成功或一起失败。它不会在 PostgreSQL 提交时打电话回来问：文档那一行写进去了没有。RocketMQ 的回查没有对等物。

移植时把承诺写成数据库里的一张待发送表。

本地事务里同时做两件事：更新业务行，插入一条待发送记录。事务提交之后，再把记录发给 MSK，并标成已发送。进程死在中间，记录还在，补发即可。消费者按业务键做幂等，因为至少一次投递会把同一条再送来。分块看文档 id，清理看知识库 id。

待发送表就是新的回查。以前这个事实在 Broker 的半消息里，现在它在 RDS 里，和业务行同一套备份。

## 监控就挂在这两段的缝上

单机时期，队列是否在转，靠人去看。这一版把缝留成三个数。

待发送记录里最老的一条有多久。超过几分钟还没标成已发送，说明生产者到 MSK 的路断了，业务事务其实已经提交。

消费组的 lag。MSK 把这个数交给 CloudWatch。lag 涨上去，而 API 的 CPU 还很空，说明慢的是分块本身，不是问答进程。扩容时看这个数，不看 CPU。

文档停留在「执行中」的时长。消息可能已经消费完，任务却卡在模型或向量写入上。lag 看的是队列，这一项看的是业务。

三样都能告警。没有它们，多副本只是把单机的沉默复制了几份。

## 这一版明确不做什么

不在 EKS 里部署 Broker，也不为了开发环境在集群里再养一套 Kafka。本地仍可以用单节点 Kafka 把客户端跑通，生产的地址指向 MSK。

不把三个 topic 合成一个，再靠消息头分发。分块可以慢，清理要可靠，反馈可以丢。保留时间和重试次数本来就不同。

不在第一期使用跨库的分布式事务。数据库和 MSK 之间只保证：提交过的业务，最终会有一条消息；同一条消息可以重复执行。

反馈如果以后仍然只是「处理完即丢、只有一个消费者」，它可以单独留在更轻的队列里。在那之前，它跟另外两条走同一条客户端，避免两套运维。

下一篇才是改代码。三个生产者、三个消费者、现在的事务回查，从 RocketMQ 客户端换成 Kafka 客户端，并补上那张待发送表。这篇只负责记住我们为什么没有选更省事的那条路。
